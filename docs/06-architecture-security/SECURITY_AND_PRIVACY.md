# 6단계 보안과 개인정보 설계

상태: **6단계 검토 대기**

이 문서는 [시스템 구조](ARCHITECTURE.md)와 [기술 선택](TECHNOLOGY_DECISIONS.md)에 적용할 권한, 키, 개인정보, 위협과 복구 원칙을 정한다. PoC는 실제 개인정보와 가치 있는 자산을 사용하지 않지만 실제 기관형 시스템에서 필요한 책임분리와 실패 통제를 시연한다.

## 1. 보호 대상

| 보호 대상 | 잘못됐을 때의 결과 | 보호 목표 |
|---|---|---|
| 고객별 수탁권리 원장 | 권리 귀속 오류, 이중권리와 지급 오류 | 승인된 기관만 변경하고 모든 정정을 추적한다. |
| 국내 통합계좌 수량 | 무담보 발행 또는 환매 오류 | 결제와 수탁 확인, 고객 권리와 토큰 수량을 대사한다. |
| 권리토큰 | 무단 발행, 이전, 소각과 잠금 해제 | 역할분리, 직접이전 차단과 불변식 검사를 적용한다. |
| USD 장부와 시험 USDC | 이중지급, 무자금 체결과 자금 손실 | 예약, 사용, 해제와 지급을 요청 단위로 추적한다. |
| 고객 적격성 | 부적격 지갑의 보유와 거래 | 만료와 철회가 가능한 최소 결과만 체인에서 검사한다. |
| 주문과 기관 승인 | 재사용, 위조와 권한 없는 처리 | 서명, nonce, 만료, 정책 버전과 사용 여부를 검증한다. |
| 운영키와 관리자 권한 | 시스템 전체 장악과 기록 조작 | 키 분리, 다중승인, 최소권한과 긴급중지를 적용한다. |
| 합성 고객 연결정보 | 실제 구조에서의 개인정보 유출 가능성 | 공개 체인과 오프체인 연결을 분리하고 최소 수집한다. |
| 감사기록 | 사고 원인과 책임을 확인할 수 없음 | 원기록을 덮어쓰지 않고 체인과 기관 증거를 연결한다. |

## 2. 신뢰 경계

```text
고객 자기보관 지갑
        │ 서명된 주문 의사
        ▼
공개 인터넷 ─ 투자자 앱 ─ 백엔드 인증 경계
                              │
                   업무 조정과 기관 승인 경계
                    │                    │
              PostgreSQL          기관 모의 어댑터
                    │                    │
                 키 사용 경계 ─ 블록체인 RPC 경계
                                      │
                              Avalanche Fuji 공개 원장
```

- 고객 지갑 서명은 주문 의사를 증명하지만 고객 적격성, 권리와 자금을 증명하지 않는다.
- 토큰 플랫폼의 요청은 기관 승인이나 기준 기록을 대신하지 않는다.
- 기관 모의 응답도 서명, 출처와 정책 버전을 확인한 뒤에만 사용한다.
- RPC 응답은 체인 확정 영수증과 독립된 이벤트 재조회로 확인한다.
- 공개 체인의 내용은 누구나 볼 수 있다고 전제한다.

## 3. 역할과 권한 분리

| 역할 | 허용 | 금지 | 승인 또는 감시 |
|---|---|---|---|
| 고객 지갑 | 주문 의사 서명, 자기 주문 취소 | 직접 토큰이전, 발행과 소각, 적격성 변경 | 해외 증권사의 최신 적격성 필요 |
| 지정 시장조성자 지갑 | 호가와 주문 서명, 승인된 DvP 참여 | 고객 간 이전, 무재고 매도, 위험한도 우회 | 시장조성과 위험 모듈 감시 |
| 해외 증권사 적격성 담당 | 적격성 발급, 갱신과 철회 승인 | 토큰 발행과 자금 지급 실행 | 준법 기록과 만료정책 |
| 해외 증권사 권리 담당 | 권리기입, 권리종료와 지급청구 승인 | 체결 또는 T+2 위험 승인 | 권리 원장과 두 축 대사 |
| 해외 증권사 위험 담당 | T+2 위험과 시장조성 한도 승인 | 권리 원장 또는 토큰 변경 | 한도와 승인 이력 |
| 발행 실행 주체 | 승인된 수량의 발행 요청 실행 | 이전, 복구와 임의 발행 | 체결, 위험과 권리기입 증거 필요 |
| 정산 실행 주체 | 승인된 투자자와 시장조성자 거래 실행 | 일반 P2P와 승인 없는 강제이전 | 주문과 승인 nonce 및 만료 검사 |
| 소각 실행 주체 | 승인된 환매수량 소각 | 발행, 이전과 임의 소각 | 지급청구와 매도대금 증거 필요 |
| 복구 실행 주체 | 승인된 지갑 교체 실행 | 권리 변경과 단독 복구 | 권리 담당과 독립 준법 승인 필요 |
| 긴급중지 주체 | 종목 또는 전체 신규 실행 중지 | 단독 재개와 기록삭제 | 모든 중지 이벤트를 감사기록에 연결 |
| 관리자 다중서명 | 역할변경, 정책변경과 재개 승인 | 일상 주문, 발행과 정산 | 2-of-3 승인과 지연 적용 |
| 준법과 감사 | 대사, 격리, 보정안과 재개 검토 | 원기록 변경과 단독 실행 | 독립 승인 이력 |

하나의 실제 사람이 PoC에서 여러 역할을 시연할 수는 있지만 계정, 서명과 승인기록은 역할별로 분리한다. 기관 콘솔의 역할화면 전환은 권한상승 수단이 아니다.

## 4. 관리자와 운영키

### 4.1 관리자

- 최고 관리자 권한은 3개 독립 시험 서명자 중 2개가 필요한 다중서명으로 둔다.
- 역할 부여 및 회수, 적격성 발급자 변경, 중요 정책변경과 중지 후 재개는 관리자 승인이 필요하다.
- 중요 변경은 즉시 실행하지 않고 사전에 기록한 지연 뒤 실행한다. 정확한 지연시간은 8단계에서 정한다.
- 초기 배포 계정은 역할 구성을 끝낸 뒤 관리자 권한을 보유하지 않는다.

### 4.2 운영키

- 발행, 정산, 소각, 적격성, 복구와 긴급중지는 서로 다른 키를 사용한다.
- 운영키는 필요한 기능만 호출할 수 있고 관리자 역할을 부여받지 않는다.
- 긴급중지 키는 즉시 중지할 수 있지만 재개할 수 없다.
- PoC 운영키는 암호화된 로컬 키 저장소에 둔다. 평문 개인키, 니모닉, API 키와 데이터베이스 비밀번호를 저장소에 커밋하지 않는다.
- 자동시험 키는 시험 전용으로 생성하고 Fuji의 경제적 가치 있는 자산을 보유하지 않는다.
- 로그에는 개인키, 서명 원문과 인증 토큰을 남기지 않는다.

### 4.3 키 사고

- 운영키 탈취가 의심되면 해당 역할과 영향을 받는 기능을 즉시 중지한다.
- 관리자 다중서명이 손상된 키를 회수하고 새 키에 역할을 부여한다.
- 탈취기간의 모든 발행, 이전, 소각과 적격성 변경을 다시 대사한다.
- 권리 원장과 다른 체인 결과는 삭제하지 않고 격리, 보정 또는 승인된 역거래로 처리한다.

## 5. 고객 지갑과 복구

- 고객은 권리계정마다 공유되지 않는 자기보관 지갑 하나를 활성화한다.
- 플랫폼은 고객 개인키를 생성, 저장, 복구하거나 대신 서명하지 않는다.
- 주문은 지갑이 서명한 EIP-712 의사표시와 별도의 해외 증권사 승인을 모두 요구한다.
- 주문 서명은 체인, 정산 계약, 고객, 종목, 수량, 방향, 가격 또는 지급금액, nonce와 만료에 묶는다. 정확한 필드는 7단계에서 정한다.
- 지갑 분실이나 탈취 때 기존 지갑을 먼저 동결한다.
- 해외 증권사의 계좌와 권리 담당 및 독립 준법 담당이 같은 고객의 새 지갑임을 승인해야 복구한다.
- 복구는 고객별 수탁권리 원장의 수량을 바꾸지 않는다. 토큰 이동과 기존 지갑 철회를 연결해 감사한다.

## 6. 개인정보 최소화

### 6.1 저장하지 않는 정보

- 실제 이름, 생년월일, 여권번호, 주소와 연락처
- 실제 국적, 조세거주지, 제재조회 결과 원문
- 실제 은행계좌와 증권계좌 번호
- 여권번호나 고유식별정보의 해시

PoC는 허용, 거절, 만료 상태가 사전 구성된 합성 고객만 사용한다.

### 6.2 오프체인에만 두는 정보

- 합성 고객 식별자와 지갑 연결
- 계좌, 고객권리와 주문의 연결
- 투자자보호 판정과 공시 동의
- 기관 승인 원문, 민원과 월별 보고 증거
- 지갑 복구 근거와 승인자

### 6.3 온체인에 둘 수 있는 최소 정보

- 지갑 주소와 권리토큰 잔액
- 지갑의 현재 거래 가능 여부, 지정 시장조성자 여부와 만료 및 철회 상태
- 종목 식별값, 수량, 주문 또는 승인 nonce와 만료
- 정책 버전과 기관 증거의 비식별 해시
- 발행, 이전, 동결, 중지, 복구와 소각 이벤트

판매 국가, 국적, 세율과 제재검사 결과를 평문 클레임으로 기록하지 않는다. 적격성 판단에 필요한 여러 오프체인 결과를 하나의 최소 거래 가능 결과로 줄인다.

## 7. 주요 위협과 통제

| 위협 | 예방 | 탐지 | 격리와 복구 | 책임 |
|---|---|---|---|---|
| 무승인 발행 | 발행 실행 주체 분리, 체결, 위험과 권리기입 완료 증거 및 일회성 nonce | 발행수량과 권리 원장 대사 | 해당 종목 신규 발행과 24/7 중지, 권리만 있는 요청 격리 | 해외 증권사 권리와 위험 담당, 토큰 운영 |

| 고객 직접이전 | 일반 transfer 경로 차단, 정산 통제만 이전권한 보유 | 정산 요청 없는 이전 이벤트 감시 | 해당 토큰 중지와 권리 및 토큰 재대사 | 토큰 운영, 준법 |

| 무재고 시장조성자 매도 | 결제완료 재고 예약과 순포지션 한도 | 호가와 체결 전후 재고 대사 | 위험을 늘리는 호가 중지, 헤지 대기 | 시장조성과 위험 담당 |
| USD 장부와 체인 일부 완료 | 예약, 요청별 순서와 최종 완료 게이트 | 체인 영수증과 권리 및 자금 확정 비교 | 요청 수량과 자금 격리, 승인된 보정 | 해외 증권사 자금과 권리 담당 |
| USDC DvP 실패 | 같은 체인 거래에서 양 자산 이전 | 거래 실패와 실제 잔액 확인 | 예약 해제, 기존 상태 유지 | 정산 실행 주체 |
| USDC DvP 뒤 권리 원장 실패 | 사전 승인과 원장 확정 대기 | 체인 결과와 권리 원장 비교 | 관련 지갑 및 수량 격리, 보정 또는 역거래 승인 | 해외 증권사 권리 담당, 준법 |
| 환매 소각 또는 USD 지급 일부 실패 | 지급청구, 소각과 지급을 한 요청에 연결 | 소각 대기 토큰과 지급청구 대사 | 요청 격리, 확인된 단계부터 재실행 | 환매 및 자금 담당 |
| 오래된 가격, 환율과 위험정보 | 기준시각, 수신시각, 유효기한 검사 | 만료와 출처충돌 경보 | 승인된 업무범위만 중지 | 시장과 기준정보 담당 |
| 위조된 기관 응답 | 허용된 기관 서명자, 정책 버전과 원문 해시 확인 | 서명 실패와 알 수 없는 발급자 경보 | 응답 거절, 관련 어댑터 중지 | 기관 연계 담당 |
| RPC 오류나 잘못된 영수증 | 요청 전 체인과 계약 확인, 확정 영수증 검증 | 독립 재조회와 블록 높이 감시 | 미확정 유지, 다른 RPC로 재조회 | 블록체인 운영 |
| 운영키 탈취 | 키 분리, 암호화 저장, 최소권한 | 비정상 시간, 수량과 호출 경보 | 역할 회수, 기능중지와 전기간 재대사 | 보안 담당, 관리자 다중서명 |
| 관리자 권한 남용 | 2-of-3 승인, 변경지연과 역할분리 | 예약과 실행 이벤트 및 승인자 감사 | 예약 취소, 긴급중지와 독립 검토 | 관리자, 감사 |
| 개인정보 연결과 공개 | 합성정보만 사용, 온체인 최소화 | 로그와 배포자료 검사 | 노출 화면 중지, 자료 제거와 원인검토 | 개인정보와 보안 담당 |
| 서비스 중단과 재시작 | PostgreSQL 요청과 발송함, 멱등 재실행 | 미처리 작업과 지연시간 감시 | 기존 요청 재개, 만료 예약 해제 | 플랫폼 운영 |

## 8. 사건별 중지와 재개

중지는 원인에 맞는 가장 좁은 범위로 적용한다.

- 고객 적격성 만료: 해당 고객의 신규 주문과 권리수령
- USDC 가격 이탈: USDC 경로
- 가격, 환율 또는 시장정보 지연: 24/7 호가와 체결
- 시장조성자 위험한도: 위험을 늘리는 방향의 새 호가
- KRX 거래정지 또는 중요사건: 신규 1차 발행, 시장조성자 헤지 제출과 24/7 거래
- 비현금 기업행동: 해당 종목의 발행, 24/7 거래와 환매
- 권리와 토큰 대사 불일치: 신규 발행과 24/7 거래
- 관리자 또는 발행키 탈취: 영향받는 권한과 필요시 전체 토큰 실행

재개에는 원인 기록 관리자의 보정, 전체 재대사와 독립된 준법 또는 감사 담당의 승인이 필요하다. 긴급중지 키는 재개할 수 없다.

## 9. 감사와 변경 이력

- 요청, 승인, 기관 응답, 체인 거래, 중지, 격리, 보정과 재개를 하나의 요청 흐름으로 연결한다.
- 원기록은 덮어쓰지 않는다. 정정은 이전 기록을 가리키는 새 기록으로 남긴다.
- 체인 거래 해시, 계약주소, 블록, 실제 수량과 이벤트를 저장한다.
- 누가 어떤 역할로 무엇을 승인했는지와 적용 정책 버전을 기록한다.
- 같은 증거나 승인이 다른 요청에 쓰였는지 검사한다.
- 감사화면과 로그에 원본 개인정보, 비밀키, 인증토큰과 전체 서명을 표시하지 않는다.
- 월별 보고는 원본 개인정보 없이 생성, 제출, 접수, 정정과 10년 보관 증거만 시연한다.

## 10. 안전한 개발 기준

- 개발과 검토 절차는 [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final)을 참고한다.
- 웹과 API는 [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)의 인증, 접근통제, 입력검증, 로그와 오류처리 항목을 선택 적용한다.
- EVM 계약은 [OWASP Smart Contract Security Verification Standard](https://github.com/OWASP/www-project-smart-contract-security-verification-standard)를 참고한다.
- 역할관리에는 [OpenZeppelin 접근통제 지침](https://docs.openzeppelin.com/contracts/5.x/access-control)의 최소권한, 관리자 다중서명과 지연 원칙을 참고한다.
- 의존성 버전을 고정하고 잠금파일을 보존한다.
- 비밀정보 탐지, 정적분석, 단위시험과 불변식 시험을 구현 검증에 포함한다.

표준을 참고한다는 것은 전체 준수, 외부 감사나 보안 인증을 받았다는 뜻이 아니다.

## 11. 보안 인수 시나리오

- 승인 없는 발행, 소각, 복구와 역할변경이 실패한다.
- 고객의 직접 transfer와 고객 간 이전이 실패한다.
- 같은 주문 또는 기관 승인 nonce를 다시 사용해도 추가 처리가 생기지 않는다.
- 결제 대기 또는 환매 잠금 수량을 이전할 수 없다.
- USD 체인 이전 뒤 권리와 자금 확정 실패가 완료로 표시되지 않고 격리된다.
- USDC와 토큰 중 하나만 이동하려는 DvP가 전체 실패한다.
- 체인 DvP 뒤 권리 원장 실패가 관련 수량을 격리한다.
- 적격성 만료와 철회가 신규 거래를 막는다.
- 운영키 하나가 탈취돼도 관리자, 다른 실행권한과 권리 원장을 바꿀 수 없다.
- 긴급중지는 즉시 가능하지만 같은 키로 재개할 수 없다.
- 서비스 재시작 뒤 미처리 요청을 재개해도 중복 발행, 이전, 소각과 지급이 없다.
- 데이터베이스, 로그와 체인에서 금지된 개인정보와 비밀값이 발견되지 않는다.

## 12. 남는 한계

- 공개 체인은 합성 지갑이라도 보유량과 거래관계를 공개한다.
- PoC의 암호화 로컬 키 저장은 실제 기관 HSM이나 클라우드 KMS 운영을 입증하지 않는다.
- 모의 기관 서명은 실제 기관의 전자서명, 계약과 부인방지 효력을 입증하지 않는다.
- 블록체인 DvP는 해외 증권사 권리 원장까지 원자적으로 바꾸지 않는다.
- 실제 개인정보 처리의 적법성, 보존기간, 국외이전과 파기 절차는 별도 법률과 기관 검토가 필요하다.
- Fuji의 가용성, 수수료와 운영특성은 상용 메인넷의 서비스 수준을 보장하지 않는다.

## 13. 승인 기준

- [ ] 모든 중요한 권한에 허용 기능, 금지 기능, 승인자와 감사방법이 있다.
- [ ] 한 운영키로 발행, 이전, 소각, 복구, 중지와 재개를 모두 수행할 수 없다.
- [ ] 온체인과 오프체인 정보 분리 및 공개 체인의 개인정보 한계가 분명하다.
- [ ] 주요 위협마다 예방, 탐지, 격리와 복구 및 책임자가 연결돼 있다.
- [ ] 5단계 사건별 중지범위와 재개조건이 보안 대응에서도 유지된다.
- [ ] 보안 시연과 실제 기관 보안인증의 경계를 과장하지 않는다.

[시스템 구조](ARCHITECTURE.md), [기술 선택](TECHNOLOGY_DECISIONS.md)과 함께 승인하기 전에는 7단계를 시작하지 않는다.
