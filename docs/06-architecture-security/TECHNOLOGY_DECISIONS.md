# 6단계 기술 선택

상태: **6단계 팀 내부 승인 완료**

이 문서는 [시스템 구조](ARCHITECTURE.md)를 구현할 기술과 포기한 대안을 기록한다. 기술 선택은 PoC를 위한 것이며 실제 상품의 상용 기술이나 참여기관의 승인을 뜻하지 않는다.

## 1. 선택 원칙

- 자기보관 지갑과 통제된 24/7 이전을 눈으로 확인할 수 있어야 한다.
- 고객별 수탁권리 원장이 토큰보다 우선한다는 경계를 유지해야 한다.
- 201개 종목에 같은 규칙을 적용하고 종목별 중지와 수량을 분리할 수 있어야 한다.
- 직접이전, 무승인 발행과 소각 및 결제 대기 수량 이전을 체인에서도 막아야 한다.
- 실제 기관 연결을 모의 어댑터로 바꿔도 업무 의미가 같아야 한다.
- 구현 복잡도는 PoC가 실패 시나리오와 복구를 충분히 보여줄 수 있는 수준으로 제한한다.

## 3. 발행 블록체인

### 3.1 선택: Avalanche Fuji C-Chain

PoC의 단일 발행 체인은 `Avalanche Fuji C-Chain`으로 한다.

- 공개 테스트넷이라 자기보관 지갑의 토큰 보유와 제한 이전을 독립된 탐색기에서 확인할 수 있다.
- EVM과 Solidity를 지원해 제한형 ERC-20 잔액과 정산 통제 계약을 구현할 수 있다.
- 빠른 비가역적 완결성은 24/7 체결의 기술적 완료를 짧은 시연시간 안에 확인하기 적합하다.
- Dinari는 dShares 지원 체인에 Avalanche C-Chain을 포함하고, Dinari Financial Network를 Avalanche L1으로 설명한다. PoC가 Dinari를 그대로 복제하지는 않지만 비교 연결성이 있다.
- 후속 LayerZero V2 OFT 원칙과 EVM 도구를 유지할 수 있다.

공식 근거:

- [Avalanche Primary Network와 Fuji C-Chain](https://docs.avax.network/docs/primary-network)
- [Avalanche 완결성 설명](https://docs.avax.network/solutions/performance)
- [Dinari 지원 블록체인](https://docs.dinari.com/docs/blockchain)
- [Dinari와 Flow Traders의 Avalanche L1 설명](https://dinari.com/blog/flow-traders-and-dinari-partner-to-unlock-24-7-tokenized-equity-markets)

Fuji 선택은 상용 메인넷을 Avalanche로 확정한다는 뜻이 아니다. 실제 상품은 데이터 공개, 기관 지갑, 수수료, 규제와 운영자 계약을 다시 검토해야 한다.

## 4. 토큰 표준

### 4.1 선택: ERC-20 인터페이스 기반 제한형 권리토큰

이번 PoC는 ERC-20의 종목별 잔액, 공급량과 표준 이벤트를 사용하되 일반 사용자의 이전과 임의 승인을 막는 제한형 권리토큰을 직접 설계한다. 적격성, 결제 대기와 환매 잠금, 지갑 복구, 종목 중지와 승인된 정산 이전은 별도 레지스트리와 기능별 통제 계약이 담당한다. 따라서 이 토큰을 자유이전 가능한 일반 ERC-20 또는 완전한 ERC-20 호환 토큰이라고 표현하지 않는다.

[Dinari의 공개 DShare 계약](https://github.com/dinaricrypto/sbt-contracts/blob/main/src/DShare.sol)은 ERC-20 잔액에 발행, 소각과 이전 제한을 붙인다. 이번 PoC는 이 기본 방향을 참고하지만 단순 블랙리스트보다 강하게 적격성 만료, 상호 배타적인 수량상태, 독립 승인, 투자자와 지정 시장조성자 사이의 정산 전용 이전을 적용한다. 이는 Dinari 코드를 복사하거나 실제 운영 계약과 동일하다고 주장하는 것이 아니다.

| 필요한 기능 | 제한형 ERC-20 사용 방식 |
|---|---|
| 적격 지갑만 보유 | 최소 적격성 레지스트리에서 활성, 만료와 철회를 검사한다. |
| 결제 대기와 환매 잠금 | 거래 가능, 국내 결제 대기, 환매 잠금, 소각 대기와 관리상 동결을 상호 배타적인 수량으로 관리한다. |
| 종목 중지 | 종목별 계약을 중지한다. |
| 발행과 소각 | 체결과 배분 확인, 위험 승인, 권리기입 승인과 원장 반영 완료가 일치할 때 승인된 별도 통제 계약만 실행한다. |
| 지갑 복구 | 해외 증권사 권리 원장과 독립 승인을 확인한 복구 통제만 실행한다. |
| 지정 시장조성자 거래 | 정산 통제 계약이 투자자와 지정 시장조성자 조합만 허용한다. |

ERC-3643은 적격성 검사, 동결, 복구와 관리 기능을 비교하는 참고 표준으로만 남긴다. 공식 규격은 ONCHAINID와 조건부 일반 이전을 전제로 하므로, 인가 해외 증권사의 오프체인 적격성 판정이 기준이고 일반 이전을 전면 차단하는 이번 PoC에 ONCHAINID와 클레임 계약을 추가하지 않는다. [ERC-3643 공식 규격](https://eips.ethereum.org/EIPS/eip-3643)을 따르는 실제 기관 사례가 있다는 사실은 이 PoC에 해당 표준이 필수라는 뜻이 아니다.

### 4.2 직접이전 제한

- 고객과 시장조성자가 일반 `transfer`, `transferFrom`이나 임의 `approve`로 토큰 이동 권한을 만드는 경로는 항상 실패해야 한다.
- 고객은 플랫폼 화면에서 주문 의사를 EIP-712 형식으로 서명한다.
- 인가 해외 증권사는 적격성, 결제완료 권리, 자금과 위험한도를 승인한다.
- 정산 통제 계약만 주문, 승인, 만료, nonce와 거래상대 역할을 검증한 뒤 토큰 이전을 실행한다.
- 한 번 사용한 주문과 승인 nonce는 다시 사용할 수 없다.
- 정확한 함수, 서명 데이터와 실행 권한은 7단계와 8단계에서 정한다.

정산 전용 함수는 일반 관리자나 외부 계정이 직접 호출하는 강제이전 경로가 아니다. 고객 주문, 시장조성자 호가, 인가 해외 증권사 승인, 적격성, 수량상태, 만료와 nonce를 코드로 검사하는 정산 통제 계약만 호출할 수 있다. 발행, 정산, 환매와 복구 통제 계약에는 서로 다른 최소 역할을 부여한다.

### 4.3 포기한 표준

| 대안 | 판단 |
|---|---|
| 자유이전 가능한 일반 ERC-20 | DeFi 호환은 쉽지만 플랫폼 밖 P2P 이전과 결제 대기 수량 이전을 막지 못하므로 제외한다. |
| ERC-3643 전체 구성 | 적격성, 동결과 복구 인터페이스는 유용하지만 ONCHAINID와 클레임 레지스트리가 해외 증권사의 기준 판정을 중복하고 조건부 일반 이전 모델이 이번 전면 차단 원칙과 맞지 않는다. |
| ERC-1400 | 파티션과 증권형 기능은 참고할 수 있지만 이번 단일 권리단위보다 복잡하다. |
| ERC-1155 한 계약 다종목 | 201종목 등록은 단순해지지만 종목별 공급량, 중지, 탐색기 표시와 개별 계약 대사가 약해 제외한다. |
| ERC-4626 | 예치자산에 대한 금고 지분 또는 래핑 표준이다. Dinari도 별도 wrapped dShare에 사용하며 개별 dShare 자체의 권리토큰 표준은 아니므로 이번 단일체인 PoC에서 사용하지 않는다. |

## 5. 종목별 배포 구조

- KRX 종목코드와 공식 ISIN이 모두 확인된 상품만 계약 배포 후보가 된다.
- 종목별로 별도 권리토큰 계약을 둔다. 이름, 코드, 소수점 0, 상품 식별값과 해당 종목의 상태를 분리한다.
- KOSPI 200 기준 스냅샷 201개를 오프체인 상품 레지스트리에 등록하고 모두 같은 배포 전 검증을 거친다.
- Fuji에는 공식 종목코드와 ISIN을 확인한 대표 6종목만 공통 팩토리로 같은 구현을 직접 배포한다. 나머지 종목은 배포 후보와 공통 설정 검증까지만 수행하며 실제 계약주소나 공급량이 있다고 표시하지 않는다.
- 적격성 레지스트리와 역할통제는 공유하되 종목별 공급량, 동결, 기업행동 중지와 대사는 각각 유지한다.
- 배포 주소와 상품 식별자의 연결은 7단계 기준정보와 배포기록에서 관리한다.
- 구현 코드는 고정된 버전을 사용한다. 묵시적으로 계약 코드를 바꾸는 업그레이드는 사용하지 않고 정책과 역할 변경만 승인 절차로 허용한다. 코드 변경은 새 배포와 명시적 전환안이 필요하다.

## 6. 온체인 적격성

- 원본 고객확인, 국적, 여권, 계좌와 판매판정 근거는 오프체인에 둔다.
- 온체인에는 지갑이 현재 거래 가능한지, 지정 시장조성자인지, 언제 만료 또는 철회됐는지만 최소화해 반영한다.
- 판매 국가, 조세거주지와 제재검사 원문은 공개하지 않는다.
- 적격성 발급, 갱신과 철회는 인가 해외 증권사 모의 승인에 따라 별도 역할이 수행한다.
- 지갑과 실명고객 연결은 공개하지 않지만 공개 체인의 거래관계 자체는 숨길 수 없음을 화면과 한계에 표시한다.

ONCHAINID와 온체인 클레임 계약은 배포하지 않는다. 인가 해외 증권사의 여러 오프체인 판정은 거래 가능 여부, 지정 시장조성자 여부, 만료와 철회라는 최소 결과로만 줄여 적격성 레지스트리에 기록한다. 원본 개인정보와 식별정보 해시는 온체인에 두지 않는다.

## 7. USD와 USDC 정산 기술

### 7.1 USD 경로

- USD는 해외 증권사의 모의 고객자금 장부 값이다.
- 체결 전 구매자 USD와 판매자 권리 및 토큰을 요청별로 예약한다.
- 정산 통제 계약의 토큰 이전과 해외 증권사 권리 및 자금 장부 확정을 업무 조정기가 순서대로 처리한다.
- 외부 장부와 체인은 원자적이지 않으므로 한쪽 확정 뒤 실패하면 관련 수량과 자금을 격리하고 보정한다.

### 7.2 USDC 경로

- 자동시험은 6자리 소수점을 가진 모의 USDC를 로컬 EVM에 배포한다.
- Fuji 수동 시연은 이용 가능한 Circle 계열 시험 USDC를 우선 사용한다. 사용 불가 또는 공급 중단 시 같은 인터페이스의 명시된 모의 USDC로 바꾸고 그 사실을 결과보고서에 남긴다.
- 정산 통제 계약은 같은 거래 안에서 시험 USDC와 권리토큰을 양방향 이전한다.
- 거래금액은 지정 시장조성자의 서명된 호가와 확정수량으로 계산하며 외부 가격 오라클이 결정하지 않는다.
- 해외 증권사의 권리 원장 확정은 온체인 DvP 밖의 업무이므로 확인 전까지 전체 업무는 완료가 아니다.

### 7.3 1차 발행과 환매

- 1차 발행의 USDC는 모의 전환사업자가 USD 귀속을 확인한 뒤 국내 주문에 사용한다. 기초주식과 온체인 DvP를 하지 않는다.
- 환매는 국내 매도대금 결제와 권리종료 뒤 토큰을 소각하고 USD 고객계좌로 지급한다.
- 환매대금의 USDC 재전환은 구현하지 않는다.

## 8. 외부 정보와 오라클

PoC는 탈중앙화 가격 오라클을 필수 구성요소로 사용하지 않는다.

| 정보 | PoC 원본 | 시스템 전달 | 체인 사용 |
|---|---|---|---|
| KRX 가격과 시장상태 | 공식 기준자료와 합성 갱신 | 외부 정보 수집 모듈 | 직접 기록하지 않음 |
| USD/KRW | 한국은행 기준자료와 합성 갱신 | 외부 정보 수집 모듈 | 직접 기록하지 않음 |
| USDC/USD | 합성 확인가격 | 자금경로 통제 | 허용범위 이탈 시 USDC 경로 중지 |
| 지정 시장조성자 호가 | 시장조성자 서명 | 24/7 거래 모듈 | USDC DvP의 확정금액 검증에 사용 |
| 국내 체결 | 국내 증권사 모의 응답 | 1차 주문 모듈 | 발행 승인 증거 해시만 연결 가능 |

| 고객 적격성 | 해외 증권사 모의 판정 | 고객 모듈과 적격성 레지스트리 | 최소 결과만 기록 |

각 입력은 원본기관, 기준시각, 수신시각, 유효기한, 정책 버전, 정정연결과 증거 해시를 가져야 한다. 정확한 형식은 7단계에서 정한다.

Chainlink 같은 상용 서비스는 향후 데이터 공급 후보다. 공식 KRX 전 종목 지원, 데이터 사용권, 방법론과 서비스 수준을 확인하기 전에는 필수 의존성으로 두지 않는다. 가격이 오래되거나 출처가 충돌하면 대체가격으로 자동 체결하지 않고 승인된 범위만 중지한다.

## 9. 다중체인

- 1단계 PoC는 Fuji 단일체인이다.
- LayerZero V2 OFT Burn&Mint는 후속 원칙으로만 문서화한다.
- 브리지를 도입할 때는 원천 체인 소각, 목적 체인 발행, 목적지 지갑 적격성, 해외 증권사 권리 원장 승인과 체인 합산 공급량을 함께 검사해야 한다.
- 브리지 메시지 검증자, 속도제한, 실패복구, 관리자 권한과 체인별 중지방식은 이번 단계에서 구현하지 않는다.

## 10. 확정하지 않는 세부사항

다음은 후속 단계가 정한다.

- 7단계: 공통 식별자, 데이터 필드, EIP-712 메시지, API, 이벤트와 오류 응답
- 8단계: 제한형 ERC-20 함수, 역할 식별자, 배포 팩토리, 수량상태, 정산, 잠금과 복구 구현
- 9단계: 코드 단위시험, 퍼징, 불변식, 실패주입과 인수시험의 전체 목록
- 10단계: 정확한 패키지 버전, 배포 자동화와 실행 환경

후속 단계는 Fuji, ERC-20 잔액과 이벤트 기반 제한형 토큰, 소수점 0, 종목별 계약, 직접이전 차단, USD와 USDC 경로 분리 및 오프체인 권리 원장 우선 원칙을 바꿀 수 없다. 변경이 필요하면 6단계를 다시 승인한다.
