# 6단계 시스템 구조

상태: **6단계 검토 대기**

이 문서는 승인된 [제품 요구사항](../03-product-requirements/PRD.md), [기관 업무](../04-institution-design/INSTITUTION_WORKFLOWS.md), [화면 흐름](../05-screens-states-recovery/SCREEN_FLOWS.md), [상태 모델](../05-screens-states-recovery/STATE_MODEL.md)과 [오류 및 복구 규칙](../05-screens-states-recovery/ERROR_AND_RECOVERY.md)을 실제 시스템 경계로 옮긴다. 정확한 데이터 필드와 API는 7단계, 스마트컨트랙트 함수와 권한 배치는 8단계에서 확정한다.

## 1. 구조가 지켜야 하는 기준

- 인가 해외 증권사의 고객별 수탁권리 원장이 최종투자자 권리의 기준 기록이다.
- 국내 통합계좌 수량은 KSD와 국내 계좌관리기관의 모의 확인을 기준으로 한다.
- 토큰은 고객 권리를 보여주고 이전을 통제하는 실행 기록이며 권리 원장을 대체하지 않는다.
- 플랫폼 계산값은 주문, 수량과 위험을 처리하기 위한 결과다. 기관 확인 없이 법적 사실을 만들지 않는다.
- 실제 기관, 데이터베이스와 블록체인을 하나의 원자적 거래로 묶을 수 있다고 가정하지 않는다.
- 부분 완료는 성공으로 표시하지 않는다. 재시도할 수 있으면 대기하고, 기준 기록이 충돌하면 격리한다.
- 개인정보, 고객계좌 원문과 기관 원문은 블록체인에 기록하지 않는다.

## 2. 전체 구조

```text
투자자 앱                  통합 기관 콘솔
    │                           │
    └────────── 웹 접근 계층 ────┘
                    │
            인증과 역할 확인
                    │
    ┌──────── 업무별 단일 백엔드 ────────┐
    │ 고객과 상품        1차 주문과 발행       │
    │ T+2 확인        24/7 거래          │
    │ 시장조성과 헤지    환매와 권리관리       │
    │ 준법 및 대사       업무 조정기        │
    └─────────────────────────────┘
          │          │           │
     PostgreSQL   기관 모의     블록체인 연계
     업무와 증거      어댑터         및 감시
          │          │           │
     감사기록     KRX와 KSD        Avalanche
     발송함       수탁과 자금       Fuji C-Chain
```

PoC는 여러 독립 서비스로 쪼개지 않는다. 하나의 백엔드 안에서 업무 경계를 모듈로 나누고, 데이터베이스 거래와 트랜잭션 발송함을 공유한다. 이는 구현과 장애 재현을 단순화하면서도 외부기관 어댑터와 블록체인 연계를 나중에 독립 서비스로 분리할 수 있게 한다.

## 3. 구성요소와 책임

| 구성요소 | 책임 | 기준으로 삼는 정보 | 하지 않는 일 |
|---|---|---|---|
| 투자자 앱 | 고객확인 결과, 상품, 주문, 보유권리, 24/7 호가, 환매와 권리업무 표시 | 백엔드가 역할에 맞게 제공한 결과 | 고객 권리나 거래 승인을 직접 만들지 않는다. |
| 통합 기관 콘솔 | 기관별 업무 대기열, 승인, 대사, 격리와 감사 증거 표시 | 각 기관 모의 응답과 승인기록 | 화면 역할 전환만으로 실행권한을 바꾸지 않는다. |
| 인증과 역할 확인 | 합성 사용자와 기관 담당자의 역할, 세션과 허용 행동 확인 | 합성 계정과 역할정책 | 실제 고객확인이나 기관 인사정보를 처리하지 않는다. |
| 고객과 상품 모듈 | 합성 적격성, 전용 지갑, KOSPI 200 상품과 기능별 거래 가능 여부 관리 | 해외 증권사 모의 판정, 공식 기준정보 | 원본 개인정보를 저장하지 않는다. |
| 1차 주문과 발행 모듈 | KRW 지정가 주문 취합, 체결 배분, 위험 승인, 권리기입과 발행 요청 조정 | 국내 체결, 해외 증권사 승인과 권리 원장 | KRX 체결이나 고객 권리를 스스로 승인하지 않는다. |
| T+2 확인 모듈 | 국내 결제와 수탁수량 확인을 별도로 추적하고 거래 가능 전환 요청 | 국내 결제 확인과 수탁기관 확인 | 한쪽 확인만으로 거래 가능 상태를 만들지 않는다. |
| 24/7 거래 모듈 | 지정 시장조성자 호가, 고객 주문, 예약, 부분체결과 완료조건 관리 | 서명된 호가, 고객 주문, 자금과 권리 예약 | 고객 간 자유이전이나 CLOB를 제공하지 않는다. |
| 시장조성과 헤지 모듈 | 재고, 순포지션, 손실한도, 호가 만료와 다음 KRX 개장 헤지 대기열 관리 | 시장조성자 계정, 결제완료 재고와 위험정책 | 실제 적정가격이나 수익성을 보장하지 않는다. |
| 환매와 권리관리 모듈 | 환매, 권리종료, 지급청구, 소각, 배당, 의결권과 월별 보고 조정 | 해외 증권사 권리 원장, 국내 권리업무 확인 | 고객자금 지급이나 의결권 행사를 단독 승인하지 않는다. |
| 준법과 대사 모듈 | 두 축 수량 대사, 중지, 격리, 보정과 재개 승인 추적 | 기준시각이 같은 기관 기록과 체인 기록 | 불일치를 임의로 삭제하거나 자동 성공 처리하지 않는다. |
| 업무 조정기 | 요청별 순서, 중복방지, 재시도, 보상처리와 최종 완료 판정 | 요청기록, 승인, 기관 응답과 체인 영수증 | 기준 기록의 내용을 대신 결정하지 않는다. |
| 기관 모의 어댑터 | KRX, KSD, 국내 증권사, 수탁기관, 자금기관의 서명된 모의 응답 제공 | 사전 구성한 합성 시나리오 | 실제 기관 연결이나 법적 확인으로 표현하지 않는다. |
| 블록체인 연계와 감시 | 주문서명 검증 요청, 토큰 실행 제출, 영수증 확인과 이벤트 수집 | Fuji 확정 거래와 체인 이벤트 | 체인 성공만으로 업무상 완료를 선언하지 않는다. |
| PostgreSQL 업무 및 증거 저장소 | 요청, 상태, 기관 사본, 계산 결과, 중복방지와 감사 연결 보관 | 각 기록의 출처와 버전 | 법적 장부나 블록체인 원장을 대신하지 않는다. |

## 4. 외부기관 경계

| 외부 경계 | PoC 연결 | 전달하는 결과 | 실제와 모의의 구분 |
|---|---|---|---|
| 인가 해외 증권사 | 백엔드 안의 독립 모의 모듈 | 고객 적격성, 자금 예약, T+2 위험 승인, 권리기입과 권리 원장 결과 | 모든 화면과 기록에 모의 응답으로 표시한다. |
| 국내 주문집행 증권사와 KRX | 주문집행 어댑터 | 주문 접수, 체결, 부분체결, 정정과 취소 | 실제 주문을 보내지 않는다. |
| KSD, 수탁은행과 상임대리인 | 결제와 수탁 어댑터 | 결제완료, 수탁수량, 배당, 의결권과 기업행동 확인 | 서명된 합성 확인을 사용한다. |
| USD 자금과 환전기관 | 자금 어댑터 | USD 예약, 확정과 해제, USDC 전환과 KRW 결제재원 확인 | 실제 은행계좌와 환전을 사용하지 않는다. |
| Avalanche Fuji | 공개 테스트넷 RPC | 권리토큰과 시험 USDC 거래, 영수증과 이벤트 | 시험 토큰은 경제적 가치가 없음을 표시한다. |

모든 어댑터는 같은 업무 의미를 유지하면서 실제 기관 연결로 교체할 수 있어야 한다. 교체 가능성은 API가 같다는 뜻이 아니라 요청, 승인, 증거와 실패 책임의 의미가 같다는 뜻이다.

## 5. 정보가 놓이는 위치

| 정보 | 보관 위치 | 공개 여부 | 이유 |
|---|---|---|---|
| 고객 이름, 여권정보, 국적 원문과 계좌번호 | PoC에서 저장하지 않음 | 비공개 | 합성 고객확인만 구현한다. |
| 합성 고객 식별자와 지갑 연결 | PostgreSQL | 비공개 | 공개 주소와 고객 역할의 연결도 보호해야 한다. |
| 고객별 수탁권리 | 해외 증권사 권리 원장 모의 모듈과 확인 사본 | 비공개 | 최종투자자 권리의 기준 기록이다. |
| 국내 통합계좌 수량 | KSD와 수탁기관의 모의 응답 및 확인 사본 | 비공개 | 국내 결제완료 총보유량의 기준이다. |
| 적격성 최소 결과 | Fuji 적격성 레지스트리 | 공개 | 토큰 이전을 체인에서 차단하는 데 필요한 최소값만 둔다. |
| 토큰 잔액, 잠금과 이전 | Fuji 토큰 계약 | 공개 | 자기보관 지갑과 제한 이전을 시연한다. |
| USD 잔액과 예약 | 해외 증권사 자금 모의 장부 | 비공개 | USD는 블록체인 자산이 아니다. |
| 시험 USDC 잔액과 이전 | Fuji 시험 USDC | 공개 | USDC 경로의 모의 DvP를 시연한다. |
| 기관 응답 원문 | PostgreSQL 증거 저장소 | 비공개 | 정정과 책임 추적에 필요하다. |
| 기관 응답과 승인 증거 해시 | PostgreSQL, 필요한 경우 Fuji 이벤트 | 공개값에는 원문 없음 | 같은 증거 재사용과 변조를 탐지한다. |

Fuji는 공개 체인이므로 지갑별 토큰 잔액과 거래관계가 보인다. PoC는 이를 숨길 수 있다고 주장하지 않는다. 실제 고객과 연결되는 정보는 사용하지 않고, 상용 단계에는 공개 체인 사용의 프라이버시 적합성을 별도 검토한다.

## 6. 공통 처리 구조

모든 업무 요청은 다음 원칙을 따른다.

1. 업무 조정기가 요청 식별자와 중복방지 값을 기록한다.
2. 필요한 기관 확인과 사람 승인을 요청별 증거로 연결한다.
3. 외부 작업을 보내기 전 발송할 작업을 데이터베이스에 함께 기록한다.
4. 백그라운드 실행기가 기관 모의 어댑터나 Fuji에 작업을 보낸다.
5. 응답과 체인 영수증을 원기록에 연결하고 중복 응답은 기존 결과를 반환한다.
6. 모든 기준 기록이 같은 결과를 가리킬 때만 업무상 완료로 표시한다.
7. 일부만 확정됐으면 자동 완료하지 않고 재시도 또는 격리한다.

이를 통해 시스템 재시작 뒤에도 요청을 잃지 않고 같은 발행, 이전, 소각이나 지급을 두 번 실행하지 않게 한다.

## 7. 1차 발행과 T+2

```text
투자자 주문
  → 해외 증권사 자금과 적격성 확인
  → 국내 지정가 주문과 체결
  → 고객별 비례배분
  → T+2 위험 승인
  → 권리기입 승인과 원장 기입 완료
  → 승인된 수량만 결제 대기 토큰 발행
  → 국내 결제 확인 + 수탁수량 확인
  → 기존 토큰을 거래 가능으로 전환
```

- USD는 해외 증권사의 모의 고객자금 장부에서 예약한다.
- USDC는 시험 지갑의 수취, 모의 USD 전환과 같은 고객계좌 귀속을 확인한 뒤 USD 주문 흐름으로 들어간다.
- 권리기입 완료 뒤 블록체인 발행이 실패하면 권리만 있는 요청을 격리한다. 같은 발행 승인을 재사용하지 않고 원요청의 재실행으로 처리한다.
- 발행된 결제 대기 토큰은 고객 지갑에 보이지만 24/7 거래, 환매와 의결권에 사용할 수 없다.
- 결제와 수탁 확인이 모두 도착해야 같은 토큰을 재발행하지 않고 거래 가능으로 바꾼다.

## 8. 24/7 USD 거래

1. 지정 시장조성자가 결제완료 재고와 위험한도 안에서 서명된 지정가 호가를 낸다.
2. 고객이 호가와 만료시각을 확인하고 자기보관 지갑으로 주문 의사를 서명한다.
3. 해외 증권사 모의 모듈이 고객과 시장조성자의 적격성, 결제완료 권리와 USD를 확인한다.
4. 권리, 토큰과 USD를 요청 단위로 예약한다.
5. 정산 통제 계약이 승인된 수량의 권리토큰 이전을 실행한다.
6. 체인 영수증을 확인한 뒤 해외 증권사 권리 원장과 USD 장부를 확정한다.
7. 세 결과가 모두 확인돼야 화면에 체결 완료를 표시한다.

USD 장부와 Fuji는 기술적으로 하나의 원자적 거래가 아니다. 체인 거래 뒤 권리 원장이나 USD 확정이 실패하면 해당 요청과 수량을 즉시 격리하고 신규 사용을 차단한다. 사람은 원기록과 체인 결과를 기준으로 보정 또는 승인된 역거래를 결정한다.

## 9. 24/7 USDC 거래

1. 고객과 지정 시장조성자가 서명한 주문과 호가를 맞춘다.
2. 해외 증권사가 적격성, 결제완료 권리, 지갑과 위험한도를 승인한다.
3. 정산 통제 계약이 같은 Fuji 거래 안에서 시험 USDC와 권리토큰을 양쪽 지갑 사이에 이전한다.
4. 블록체인 연계 모듈이 확정 영수증과 실제 수량을 확인한다.
5. 해외 증권사의 고객별 수탁권리 원장을 같은 체결수량으로 확정한다.
6. 권리 원장 확인까지 끝나야 업무상 체결 완료로 표시한다.

USDC와 토큰의 온체인 교환은 함께 성공하거나 함께 실패한다. 그러나 해외 증권사 권리 원장은 외부 기록이므로 법적 또는 업무적 원자성을 주장하지 않는다. 원장 확정이 실패하면 체인 결과를 지우지 않고 관련 지갑과 수량을 격리한다.

## 10. 시장조성자 헤지와 재고조정

- 24/7 체결 뒤 시장조성자의 권리토큰 재고와 순포지션을 갱신한다.
- 위험을 줄이기 위한 헤지 수량과 방향을 계산해 다음 KRX 개장 대기열로 보낸다.
- KRX 개장 뒤 해외 증권사가 국내 주문을 승인하고 국내 증권사 모의 어댑터가 체결을 응답한다.
- 매수 헤지는 1차 발행과 T+2 절차를 거쳐 결제완료 재고를 늘린다.
- 매도 헤지는 1차 환매 절차를 거쳐 결제완료 재고를 줄인다.
- 거래정지, 외국인 한도나 위험한도 때문에 헤지할 수 없으면 대기 상태를 유지하고 위험을 늘리는 호가만 중지한다.

## 11. 1차 환매

```text
환매 요청
  → 결제완료 권리와 토큰 잠금
  → 국내 지정가 매도와 비례배분
  → T+2 매도대금 결제
  → 국내 통합계좌 수량 감소
  → 주식 수탁권리 종료
  → 환매대금 지급청구 + 소각 대기 토큰
  → 해외 증권사 승인
  → 토큰 소각 + 고객 USD 지급
```

- 매도대금 결제 전까지 주식 수탁권리와 토큰을 유지하되 다른 거래에는 사용할 수 없게 잠근다.
- 매도대금 결제가 끝나면 주식 수탁권리는 종료되고 USD 지급청구로 바뀐다.
- 소각 대기 토큰은 주식 권리수량에 포함하지 않으며 지급청구 금액과 결제증거에 연결한다.
- 소각과 USD 지급 중 하나만 끝나면 요청을 격리한다. 환매대금은 USDC로 자동 전환하지 않는다.

## 12. 배당, 의결권과 기업행동

- 배당은 국내 수령총액과 기준일 고객 권리 스냅샷을 연결하고 해외 증권사가 승인한 USD 지급으로 대사를 끝낸다.
- 고객이 선택하면 USD 지급 뒤 별도 모의 USDC 전환 요청을 만든다. 전환 실패는 배당 지급을 되돌리지 않는다.
- 의결권은 기준수량, 고객지시, 미응답과 해외 증권사 승인을 모아 상임대리인 모의 응답에 연결한다.
- 일반 의결권 수집은 거래를 멈추지 않는다.
- 비현금 기업행동은 해당 종목의 발행, 24/7 거래와 환매를 중지하고 수량변경안, 국내 반영과 전체 대사 뒤 재개한다.

## 13. 대사와 복구

두 축을 같은 기준시각으로 검사한다.

1. 해외 증권사의 고객별 수탁권리 합계와 `전체 발행토큰 - 환매 소각 대기 토큰`을 비교한다.
2. 국내 통합계좌의 결제완료 수탁수량과 투자자 및 시장조성자의 결제완료 수탁권리 합계를 비교한다.

오류가 생기면 [오류 및 복구 규칙](../05-screens-states-recovery/ERROR_AND_RECOVERY.md)의 가장 좁은 중지범위를 적용한다. 신규 발행과 24/7 거래는 대사 불일치가 해소될 때까지 중지한다. 진행 중 환매는 해당 요청의 권리, 잠금수량, 국내 매도대금과 지급수량을 독립적으로 확인할 수 있을 때만 계속한다.

## 14. 배포 구조

PoC는 다음 실행 단위를 사용한다.

- 투자자 앱과 통합 기관 콘솔
- 업무별 단일 백엔드와 백그라운드 실행기
- PostgreSQL 한 개
- KRX, KSD, 수탁과 자금용 모의 어댑터
- Avalanche Fuji RPC 연결과 체인 이벤트 감시기
- Solidity 스마트컨트랙트 묶음

개발 환경은 Docker Compose로 재현한다. Fuji가 일시적으로 사용할 수 없을 때는 로컬 EVM에서 같은 계약 시험을 실행할 수 있지만 공식 시연 결과는 Fuji 배포와 거래 영수증을 별도로 남긴다.

## 17. 승인 기준

- [ ] 모든 승인 기능에 실행 구성요소, 기준 기록과 실패 책임이 연결돼 있다.
- [ ] 고객 권리 원장, 국내 통합계좌, 토큰과 자금의 관리 주체가 뒤바뀌지 않는다.
- [ ] USD와 USDC 거래의 기술적 차이와 공통 완료조건이 분명하다.
- [ ] 부분 완료, 중복 요청, 재시작과 외부기관 지연을 처리할 위치가 정해져 있다.
- [ ] 7단계 데이터와 API 및 8단계 컨트랙트 설계가 임의로 바꿀 수 없는 경계가 분명하다.

승인 전에는 7단계 공통 데이터, API와 이벤트 설계를 시작하지 않는다.
