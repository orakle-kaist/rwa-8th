# 9단계 테스트 전략

상태: **9단계 팀 내부 승인 완료**

이 문서는 승인된 1~8단계를 10단계 구현의 합격조건으로 옮긴다. 실제 테스트 코드와 PoC는 아직 만들지 않았다. [테스트 시나리오](TEST_SCENARIOS.md), [fixture와 증거](FIXTURES_AND_EVIDENCE.md), [시연 확인표](DEMO_CHECKLIST.md)와 `specs/`의 기계 명세는 2026년 8월 31일 함께 승인됐으며 10단계 구현의 기준이다.

## 1. 검증하려는 것

- 1차 지정가 발행, T+2 전환, 24/7 제한 거래, 시장조성자 헤지, 환매와 권리업무가 승인된 순서로 끝나는가.
- 고객별 수탁권리 원장, 국내 통합계좌 수량, 토큰 수량과 고객자금이 같은 업무를 가리키는가.
- 정상적인 결제 대기와 소각 대기를 오류로 오인하지 않고 실제 불일치는 격리하는가.
- 부적격 당사자, 직접이전, 증거 재사용, 부분 완료와 잘못된 권한을 차단하는가.
- 장애와 재시작 뒤에도 발행, 이전, 소각과 지급이 한 번만 반영되는가.

가격 공정성, 실제 유동성, 시장조성자 수익성, 성능 SLA, 인허가 적합성, 실제 기관 기록과 체인의 법적 원자성은 통과 주장에 포함하지 않는다.

## 2. 테스트 계층

| 계층 | 도구와 환경 | 검증 대상 | 포함하지 않는 것 |
|---|---|---|---|
| 문서와 계약 | 저장소 검증기, JSON Schema, OpenAPI와 AsyncAPI 검사 | 문서 존재, 기계 명세, 참조, fixture와 상위 결정의 일치 | 제품 동작 |
| 업무 단위 | Vitest, 주입 가능한 시계와 통제 가능한 mock | 비례배분, 상태전환, 중복방지, 위험 및 중지 규칙 | 데이터베이스와 체인 |
| 업무 통합 | Vitest, 실제 PostgreSQL, 기관 모의 어댑터, Anvil | API 접수, 발송함, 이벤트 순번, 재시작, 권리와 체인 연계 | 공개 테스트넷 가용성 |
| 계약 | Foundry와 Anvil | 함수, 이벤트, 역할, 서명, 퍼징, handler 기반 불변식과 DvP | 해외 증권사의 실제 권리 원장 |
| 브라우저 생애주기 | Playwright Chromium | 투자자 앱과 기관 콘솔의 표시, 행동, 차단 사유와 전체 흐름 | Firefox와 WebKit 호환성 |
| Fuji 시연 | Avalanche Fuji, 대표 6종목, 시험 USDC | 공개 배포, 주소 분리, 권한, 직접이전 차단과 대표 생애주기 | 상용 체인 적합성 |

PostgreSQL 통합시험은 SQLite로 대체하지 않는다. 브라우저 합격 게이트는 Chromium 하나로 고정한다. TypeScript 패키지와 Foundry 의존성의 정확한 버전은 10단계에서 잠금파일로 고정한다.

## 3. 실행 프로필

### 빠른 검증

- 문서, 링크, JSON, JSONL, schema와 manifest 검사
- TypeScript 순수 업무 단위시험
- Foundry 계약 단위시험
- 커밋 전 반복 실행한다.

### 전체 로컬 검증

- 빠른 검증 전부
- 실제 PostgreSQL과 Anvil을 사용한 통합시험
- 오류주입, 이벤트 중복과 순번 공백, 프로세스 재시작
- Foundry 퍼징과 불변식 시험
- Playwright Chromium 전체 생애주기
- 10단계 구현 완료와 시연 후보 생성의 필수 게이트다.

### Fuji 시연 검증

- 전체 로컬 검증을 통과한 같은 커밋에서만 실행한다.
- 공식 ISIN이 확인된 대표 6종목을 서로 다른 주소로 배포한다.
- 삼성전자 대표 흐름과 직접이전 차단을 확인한다.
- 최종 시연 전 필수지만 일상적인 개발과 모든 커밋의 게이트로 사용하지 않는다.

## 4. 테스트 우선순위와 자동화

| 구분 | 의미 | 승인 조건 |
|---|---|---|
| 필수 | 제품 권리, 수량, 자금, 권한, 생애주기 또는 핵심 화면을 검증 | 건너뜀과 자동 재시도 없이 모두 통과 |
| 보조 | 설명문구, 추가 화면과 진단 편의성을 검증 | 실패 원인과 처리결정을 기록 |
| 외부 확인 | 규제, 기관계약, 가격과 시장성처럼 PoC가 입증할 수 없는 항목 | 자동시험 결과에 포함하지 않고 별도 표시 |

업무 로직, API, 데이터베이스, 계약 불변식과 핵심 브라우저 흐름은 필수 자동시험으로 만든다. 투자자 공시의 이해 가능성, 기관 관점 설명과 실제 Fuji 탐색기 확인은 사람 확인표도 함께 사용한다.

## 5. 통과 기준

- 모든 필수 테스트가 같은 시연 후보 커밋에서 통과한다.
- 필수 테스트에는 `skip`, `todo`, 조건부 무시와 자동 재시도를 허용하지 않는다.
- 실패한 테스트를 코드나 입력 수정 없이 반복해 통과시킨 결과는 증거로 인정하지 않는다.
- 모든 PRD 요구사항은 정상 사례를 하나 이상 갖는다. 차단 요구사항은 부정 사례도 하나 이상 갖는다. 요구사항에서 시험으로 가는 연결과 시험의 `requirementIds`에서 요구사항으로 돌아가는 연결이 모두 일치해야 한다.
- 상태 카탈로그의 174개 상태를 개별 항목으로 추적한다. [상태 모델](../05-screens-states-recovery/STATE_MODEL.md)의 허용 전환은 성공시험, 금지 전환은 실패시험을 갖고 각 시험은 자신이 검사하는 상태코드를 명시한다.
- 모든 오류 규칙은 영향범위, 자동 원복 또는 격리, 책임 역할과 재개조건을 검증한다.
- 모든 OpenAPI 동작, AsyncAPI 메시지, 계약 함수, 이벤트, 오류, 역할과 불변식을 이름별로 하나 이상의 실제 테스트에 연결한다. `ALL_*` 같은 선언형 전체포함 표시는 합격 증거로 인정하지 않는다.
- 코드 라인과 분기 커버리지는 보고하되 숫자 통과기준으로 사용하지 않는다.

## 6. 결정적 시간과 재현성

- 백엔드에는 주입 가능한 시계를 사용한다.
- Foundry에서는 블록시각 이동 기능을 사용하고 브라우저는 백엔드 시험시각을 조회한다.
- 호가 30초, 정보 60초와 61초, T+2, 월말 보고기한과 60초 관리자 지연을 실제로 기다리지 않는다.
- 각 시험은 고유한 업무 ID와 격리된 데이터베이스 상태를 사용한다.
- 무작위 시험은 실패 seed와 호출순서를 보존해 동일 반례를 재실행할 수 있어야 한다.

## 7. 실패주입 원칙

다음 경계에는 실행 전, 실행 후 응답 유실과 부분 완료 실패를 각각 주입한다.

- PostgreSQL 업무기록과 발송함
- 기관 요청 발송과 결과 수신
- 체인 제출, 채굴과 영수증 조회
- 권리 원장, USD 장부와 체인 확정
- USDC와 권리토큰 DvP
- 환매 권리종료, USD 지급과 토큰 소각

기준 기록이 바뀌지 않았으면 자동 원복 또는 기존 결과 반환을 기대한다. 하나라도 바뀌었거나 결과가 불명확하면 성공 처리하지 않고 격리와 사람 검토를 기대한다.

## 8. 테스트 증거

필수 실행은 다음을 하나의 실행 ID로 연결한다.

- 실행한 커밋과 명세 버전
- fixture 버전과 시뮬레이션 표시
- 구조화된 테스트 결과와 실패 로그
- 테스트 전후 권리, 토큰, 국내 수량, 자금과 시장조성자 재고 스냅샷
- Playwright 실패 trace와 화면 증거
- Foundry 실패 seed와 호출순서
- 체인 주소, 거래 영수증과 이벤트
- 자동 중지와 사람 승인 기록

개인정보, 비밀키, 전체 서명, 인증토큰과 기관 원문은 증거에 저장하지 않는다.

## 9. 9단계 승인 기준

- [x] 테스트 계층과 실행 프로필이 승인된 기술 구조와 일치한다.
- [x] 모든 PRD 요구사항, 상태, 오류와 계약 manifest 항목이 테스트에 연결된다.
- [x] 정상, 경계, 실패, 복구와 중복처리 시나리오의 기대결과가 결정됐다.
- [x] 합성 fixture가 승인된 PoC 시험값과 일치하고 실제값처럼 표현되지 않는다.
- [x] 전체 로컬 검증과 Fuji 시연 검증의 경계 및 증거가 분명하다.
- [x] 10단계 구현자가 추가 제품 결정을 내릴 항목이 남지 않았다.

`specs/test-catalog.schema.json`과 `specs/traceability.schema.json`은 필수 입력, 실행순서, 시작·기대·금지 상태, 수량·금액·오류, 원복 또는 격리, 재개조건과 증거가 비어 있지 않은지 검사한다. 저장소 검증기는 49개 요구사항, 174개 상태, OpenAPI와 AsyncAPI, ABI 및 manifest 항목의 양방향 연결을 확인한다.
