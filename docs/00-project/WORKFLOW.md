# 프로젝트 산출물과 승인 순서

이 문서는 마스터 제안서 검토부터 PoC 결과 보고까지의 작업 순서를 정합니다. 앞 단계에서 결정하지 않은 내용을 뒤 단계의 작성자나 AI가 임의로 정하지 않게 하는 것이 목적입니다.

1단계 [마스터 문서](../01-master/MASTER.md)는 2026년 8월 29일, 2~5단계 문서는 2026년 8월 30일 팀 내부 기준으로 승인했다. 이후 단계 간 정합성을 보완해 1~5단계를 같은 날 다시 승인했다. [시스템 구조](../06-architecture-security/ARCHITECTURE.md), [기술 선택](../06-architecture-security/TECHNOLOGY_DECISIONS.md)과 [보안 및 개인정보](../06-architecture-security/SECURITY_AND_PRIVACY.md)는 2026년 8월 31일 승인했다. [공통 데이터](../07-data-api-events/DATA_MODEL.md), [API 계약](../07-data-api-events/API_CONTRACTS.md), [이벤트 계약](../07-data-api-events/EVENT_CONTRACTS.md)과 기계 명세도 2026년 8월 31일 승인했다. 다음 단계는 **8단계 스마트컨트랙트 설계**다.

## 기본 원칙

- 각 단계는 바로 앞 단계에서 승인한 내용을 기준으로 시작합니다.
- 앞 단계의 결정이 바뀌면 영향을 받는 뒤 문서도 다시 검토합니다.
- 필요한 문서와 폴더는 해당 단계가 시작될 때 만듭니다.
- 확인된 사실, 팀의 해석, PoC에서 선택한 방식, 외부 확인이 필요한 사항을 구분합니다.
- AI는 확정된 설계를 구현합니다. 사람은 구현 결과가 설계와 일치하는지 확인합니다.
- 기능 하나가 끝날 때마다 검증하고 커밋합니다. 원격 저장소에는 사용자 확인을 받은 뒤 푸시합니다.

## 문서 작성 원칙

- 기관 실무자가 기술 배경 없이도 이해할 수 있는 표현을 사용합니다.
- 꼭 필요한 전문 용어는 처음 등장할 때 쉬운 말로 설명합니다.
- 긴 나열은 쉼표로 이어 붙이지 않고 문장이나 목록으로 나눕니다.
- 가운데점은 나열 기호로 사용하지 않습니다.
- 확인하지 못한 운영 방식은 사실처럼 쓰지 않습니다.

## 단계별 산출물과 승인 기준

| 단계 | 무엇을 만드는가 | 무엇을 확인하면 다음 단계로 넘어가는가 |
|---|---|---|
| 1. 마스터 문서 확정 | 해결하려는 문제, 대상 투자자, 제안 구조, 기대 효과, 범위와 남은 규제 쟁점을 설명한 문서 | 팀이 승인 또는 수정 결정을 기록한다. 이 승인은 법률 검토나 기관 승인을 뜻하지 않는다. |
| 2. PoC 목표와 성공 기준 정리 | 핵심 가설인 `한국형 수탁 권리토큰의 통제된 24/7 2차거래`를 검증하되 이를 가능하게 하는 정수 단위 KRW 지정가 1차 발행·T+2 전환, MM 헤지·재고조정과 1차 환매까지 하나의 시연 범위로 정리한다. 기관별 책임, 지정가격별 주문 취합·비례배분, 수량 불변식, 중복 방지와 복구 기준을 확정하고 가격 및 합성값은 별도 시험자료로 관리한다. | 1차 발행부터 환매대금 지급청구 전환, 토큰 소각과 USD 지급까지의 기관 인계, 결제 대기와 결제 완료 재고, 권리·토큰·자금의 함께 반영, 국내 총량, MM 위험·헤지, 중복처리 방지와 모의 데이터가 승인된다. 실제 유동성·가격 공정성·규제·사업성은 외부 검증사항으로 분리된다. |
| 3. 제품 요구사항 문서 작성 | PRD에 투자자, 인가 해외 증권사, 국내 증권사, 수탁기관과 지정 MM의 문제를 정리하고 1차 주문 취합·발행·T+2, 24/7 지정가 거래·헤지, 환매·소각·USD 지급에 필요한 기능, 우선순위와 완료 조건을 연결한다. 특정 토큰 표준, 체인이나 데이터 사업자보다 제품이 충족해야 할 동작과 품질을 먼저 적는다. | 모든 요구사항이 마스터와 PoC 목표의 기관 인계 및 성공 기준에 연결되고 미결 사항의 담당자가 정해진다. |
| 4. 기관 업무와 기준 정보 설계 | 투자자, 해외 판매기관, 국내 증권사, 수탁기관, 은행과 토큰 운영자의 역할, 인계 절차와 예외 처리 주체를 정한다. 공통 용어, 기준 장부, 정보 관리 주체와 주요 업무 상태의 초안도 함께 정리한다. 기준일이 있는 KOSPI 200 종목정보, 종목코드, ISIN, 거래 가능 상태와 데이터 연결 정보도 별도 기준정보로 설계한다. | 주문부터 보고까지 책임 공백이 없고, 각 정보의 원본, 사본, 관리 주체와 보존 책임이 분명하다. 종목 목록이 공식 기준일과 함께 재현 가능하다. |
| 5. 화면, 상태와 오류 규칙 확정 | 역할별 화면 흐름을 먼저 초안으로 만든다. 이를 바탕으로 주문, 체결, 결제, 수탁, 발행, 이전, 환매와 보고의 상태, 전환 조건과 절대 깨지면 안 되는 규칙을 정한다. 중복 요청, 지연, 정정, 취소와 실패 뒤 복구 방법 및 역할별 권한을 최종 화면에 반영한다. | 정상, 대기, 실패, 차단과 복구가 한 가지 의미로 해석된다. 화면이 존재하지 않는 상태를 만들지 않고 사용자 판단과 기관이 확인할 증거를 빠짐없이 보여준다. |
| 6. 시스템 구조, 기술 선택과 보안 설계 | 시스템 경계, 권한, 개인정보와 키 관리를 정한다. 요구사항을 기준으로 토큰 표준, 발행할 블록체인, 종목별 배포 방식과 외부 정보를 전달하는 구조를 비교해 선택한다. 블록체인에 기록할 정보와 외부 시스템에 둘 정보, 실제 연계와 모의 연계, 장애 감지와 복구 방법도 포함한다. | 선택한 기술의 이유와 포기한 대안이 기록되고 주요 위협과 운영 위험마다 예방, 탐지 또는 복구 방법이 있다. 기술 선택이 마스터의 고객 권리와 기관 책임을 바꾸지 않는다. |
| 7. 공통 데이터, API, 이벤트 설계 | 모든 시스템이 함께 쓸 종목 식별자와 데이터 형식, 시스템 간 요청 및 알림 방식을 정한다. 가격, 환율, 기업행동, 결제와 수탁 확인의 원본, 갱신 시각, 허용 지연과 오류 응답도 정의한다. 중복 처리 방지 규칙을 포함한다. | 화면, 상태 규칙과 시스템 구조가 같은 이름과 의미를 사용하고, 오래되거나 잘못 연결된 정보를 자동으로 차단하고 검증할 수 있다. |
| 8. 스마트컨트랙트 설계 | 6단계에서 선택한 토큰 표준을 기준으로 발행, 소각, 이전 제한, 동결, 지갑 교체, 중지 권한과 변경 절차의 세부 동작을 설계한다. 종목별 계약과 공통 배포 구조의 관계도 정한다. | 기관의 기존 장부와 충돌하지 않고 권한 오용, 잘못된 종목 연결과 무담보 발행을 막는 테스트 항목이 정해진다. |
| 9. 테스트 준비와 설계 확정 | 요구사항별 테스트, 실패 시나리오, 시연용 예시 데이터와 최종 확인표를 만든다. | 구현자가 새로운 상품이나 운영 결정을 내리지 않고 개발을 시작할 수 있다. |
| 10. AI로 PoC 구현 | 승인된 설계에 따라 PoC와 자동 테스트를 구현하고 실행 절차를 작성한다. | 전체 테스트를 통과하고 설계와 다른 부분이 모두 기록되고 승인된다. |
| 11. 최종 검증, 시연, 결과 정리 | 사람이 설계 일치 여부를 확인하고 시연 결과, 측정 지표, 한계와 후속 과제를 보고서로 남긴다. | 무엇을 확인했고 무엇은 아직 확인하지 못했는지 재현 가능한 증거로 설명할 수 있다. |

4단계에서는 기관의 업무 책임과 기준 정보가 서로 맞물리므로 함께 검토하고 한 번만 승인합니다. 5단계에서는 화면 흐름 초안, 상태와 오류 규칙, 최종 화면 반영 순서로 작업하되 세 결과가 일치할 때 한 번만 승인합니다.

## 기술 선택을 기록하는 위치

마스터에는 투자자 권리, 기관 책임, 지원 대상과 변경되면 안 되는 제품 원칙을 적습니다. KOSPI 200 전체를 대상으로 한다는 결정은 상품 범위이므로 마스터에 포함합니다.

PRD에는 확인된 고객만 이전할 수 있어야 한다거나 오래된 시세에서는 주문을 막아야 한다는 식으로 필요한 동작을 적습니다. 특정 표준, 체인이나 사업자 이름은 제품 요구사항 자체가 아닌 한 넣지 않습니다.

6단계의 기술 구조 결정서에서 ERC-20 잔액과 이벤트 기반 제한형 권리토큰, Avalanche Fuji C-Chain 단일 발행, 종목별 계약과 오프체인 권위정보 전달 방식을 선택했습니다. ERC-3643 전체 구성은 해외 증권사의 적격성 판정과 중복되고 Dinari 공개 토큰 구현과도 다르므로 비교 표준으로만 남깁니다. 외부 정보 전달 대상은 KRX 가격과 시장 상태, 환율, 기업행동, 국내 체결과 결제 및 수탁 확인으로 나눕니다. 다중체인 후속 단계의 제품 원칙은 LayerZero V2 OFT Burn&Mint로 유지하지만 브리지 실행은 단일체인 1단계 PoC 범위에서 제외합니다. 세부 메시지와 컨트랙트 동작은 7단계와 8단계에서 정합니다.

기술을 바꿔도 투자자 권리와 기관 책임이 그대로라면 마스터를 수정하지 않습니다. 기술 선택으로 상품의 권리, 이전 범위, 책임기관이나 대상 고객이 바뀌면 먼저 마스터와 결정 기록을 다시 승인합니다.

## 내부 검토 방식

실제 기관이 참여하기 전까지 팀원이 다음 역할을 번갈아 맡아 검토합니다.

- 상품 담당자는 24/7 2차거래가 기존 국내 결제와 수탁 권리의 경계를 넘지 않는지 봅니다.
- 시장 담당자는 지정 마켓메이커의 재고, 지정가 호가, 위험한도, 거래중지와 개장 후 헤지 대기 규칙이 일관적인지 봅니다.
- 국내 증권사와 수탁기관 담당자는 주문, 결제, 보관, 장부 확인과 기업행동이 실제로 운영 가능한지 봅니다.
- 해외 판매와 준법 담당자는 투자자 확인, 국가별 판매 제한, 기록과 보고 책임을 봅니다.
- 은행 담당자는 입금, 환전, 결제 실패, 환불과 배당 지급을 봅니다.
- 법무 역할은 확인된 규정과 설계 가설이 구분됐는지 봅니다.
- 보안과 감사 역할은 권한 분리, 개인정보 최소화, 키 관리, 변경 기록과 복구 절차를 봅니다.
- 투자자 역할은 화면이 상품의 권리, 처리 단계, 지연과 위험을 오해 없이 보여주는지 봅니다.

검토 기록에는 역할, 판단, 근거, 남은 위험과 후속 담당자를 남깁니다. 이를 **기관 관점의 내부 가설 검토**라고 부릅니다. 실제 기관 검증, 규제 적합성 확인 또는 법률의견으로 표현하지 않습니다.

## 보안 검토 방법

보안은 시스템 구조를 설계하는 6단계에서 처음 다루는 항목이 아닙니다.

- 마스터와 PRD에서는 보호할 자산, 개인정보, 금지할 결과와 악용 가능성을 정합니다.
- 업무 흐름과 화면에서는 승인 지점, 권한 분리, 오래된 정보, 오류와 복구 방법을 표시합니다.
- 상태와 시스템 설계에서는 권한 없는 처리, 중복 처리, 정정, 취소, 장애와 키 위험을 구체화합니다.
- 구현 전에는 선택한 통제를 테스트와 연결하고, 구현 뒤에는 통과 여부와 남은 위험을 기록합니다.

개발 과정은 [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final)을 참고합니다. 웹과 API는 [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/)에서 필요한 항목을 고릅니다. EVM 계열 체인을 선택할 경우에는 현재 알파 버전인 [OWASP SCSVS v0.0.1](https://github.com/OWASP/www-project-smart-contract-security-verification-standard/releases/tag/v0.0.1)도 참고합니다. 전체 표준을 준수했다거나 외부 보안 인증을 받았다고 주장하지 않습니다.

## 문서의 우선순위

현재 [마스터](../01-master/MASTER.md)부터 [이벤트 계약](../07-data-api-events/EVENT_CONTRACTS.md)까지 1~7단계 문서와 기계 명세는 승인된 기준이다. 8단계는 이 기준을 스마트컨트랙트의 역할, 함수와 전환조건으로 옮긴다. 공식 출처와 리서치 브리프는 판단 근거이고, 내부 검토 기록은 남은 쟁점을 관리하는 자료다. [pre-PRD v1 아카이브](../../archive/pre-prd-v1/README.md)는 과거 아이디어를 보관한 참고자료이며 구현 기준이 아니다.

2단계에서는 PoC의 기준일, 대표 시연 종목, 합성 데이터와 통과조건을 별도 문서로 확정합니다. 이후에는 각 단계에서 승인한 문서가 해당 범위의 기준이 됩니다.
