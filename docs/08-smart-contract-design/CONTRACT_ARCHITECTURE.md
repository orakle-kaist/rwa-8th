# 8단계 스마트컨트랙트 구조

상태: **8단계 팀 내부 승인 완료**

이 문서는 승인된 [시스템 구조](../06-architecture-security/ARCHITECTURE.md), [기술 선택](../06-architecture-security/TECHNOLOGY_DECISIONS.md), [공통 데이터](../07-data-api-events/DATA_MODEL.md)와 [이벤트 계약](../07-data-api-events/EVENT_CONTRACTS.md)을 Avalanche Fuji의 계약 경계로 옮긴다. Solidity 구현과 배포는 10단계에서 한다.

## 1. 바뀌지 않는 경계

- 인가 해외 증권사의 고객별 수탁권리 원장이 투자자 권리의 기준 기록이다.
- 토큰은 권리 원장과 일치시켜야 하는 공개 실행 기록이며 한국의 법정 주주명부나 해외 증권사의 권리 원장을 대체하지 않는다.
- 국내 결제완료 총보유량은 KSD와 수탁기관의 모의 확인을 기준으로 한다.
- 외부기관 기록과 블록체인을 하나의 원자적 거래로 만들 수 있다고 가정하지 않는다.
- 일반 개인 간 전송은 허용하지 않는다. 투자자와 지정 시장조성자 사이의 승인된 정산만 가능하다.
- `1주 = 고객 수탁권리 1단위 = 토큰 1단위`이며 소수 수량을 만들지 않는다.

## 2. 계약 관계

```text
Safe 2-of-3
    │ 제안, 승인
OpenZeppelin 지연 실행 계약 (PoC 60초)
    │ 관리자, 재개, 정책 변경
    ├── EligibilityRegistry
    ├── SecurityTokenFactory ───── 종목별 RestrictedEquityToken
    ├── MarketPolicyRegistry                ▲
    └── 역할 부여, 회수                       │ 제한 실행
                                             │
IntentVerifier ◀── 다섯 EIP-712 서명형       │
    ▲                                        │
    ├── IssuanceController ──────────────────┤
    ├── SecondarySettlementController ───────┤── 시험 USDC
    ├── RedemptionController ────────────────┤
    ├── RecoveryController ──────────────────┤
    └── CorporateActionController ───────────┘
```

계약은 프록시로 업그레이드하지 않는다. 코드가 바뀌면 설계 버전이 다른 새 계약을 배포하고, 승인된 이전 절차를 별도로 수행한다.

## 3. 계약별 책임

| 계약 | 책임 | 하지 않는 일 |
|---|---|---|
| `RestrictedEquityToken` | ERC-20의 표시정보, 잔액, 공급량과 `Transfer` 이벤트, 종목별 다섯 수량 상태, 제한된 발행, 이전, 잠금, 소각, 복구와 수량조정 | 적격성, 기관 권리와 자금의 사실을 스스로 판단하지 않는다. |
| `EligibilityRegistry` | 지갑의 거래 가능 여부, 지정 시장조성자 여부, 만료와 철회 | 고객 신원, 국적, 여권번호와 판매관할 원문을 저장하지 않는다. |
| `SecurityTokenFactory` | KRX 종목코드, ISIN, 설계 버전 중복 방지와 종목별 계약 직접 배포, 등록 | 프록시를 배포하거나 미확인 ISIN을 활성화하지 않는다. |
| `IntentVerifier` | 다섯 EIP-712 서명, 계약지갑 서명, 만료, 정책버전, nonce 검증과 성공 시 소비 | 주문을 매칭하거나 토큰, 자금을 직접 옮기지 않는다. |
| `IssuanceController` | 국내 체결과 배분 확인, T+2 위험 승인, 권리기입 승인, 권리 원장 반영 완료, 국내 결제와 수탁 확인에 따른 발행과 전환 | 체결과 배분, 위험, 권리 승인과 원장 반영 사실을 스스로 만들거나 단독 승인하지 않는다. |
| `SecondarySettlementController` | 투자자 주문, 시장조성자 호가와 해외 증권사 승인을 검증한 USD, USDC 24/7 정산 | 고객 간 거래, 결제 대기 수량 이전과 업무상 최종 완료를 단독 선언하지 않는다. |
| `RedemptionController` | 환매 잠금, 권리종료와 지급청구 전환, 소각 대기와 소각 | 국내 주식 매도나 USD 지급을 직접 수행하지 않는다. |
| `RecoveryController` | 분실, 교체 지갑의 모든 수량 상태를 새 전용 지갑으로 이전 | 고객 권리를 새로 만들거나 총발행량을 바꾸지 않는다. |
| `CorporateActionController` | 독립 승인된 비현금 기업행동 수량조정 | 소수 잔여분을 임의 반올림하거나 자동 현금화하지 않는다. |
| `MarketPolicyRegistry` | 종목과 자금경로별 발행, 정산, 환매 중지, 긴급중지와 지연 재개 | 가격이나 규제 사실을 스스로 생성하지 않는다. |

## 4. 종목 배포

`SecurityTokenFactory`는 종목코드, 공식 ISIN과 설계 버전으로 결정적인 배포 식별값을 만든다. 같은 조합은 다시 배포할 수 없다. 주소는 종목코드와 ISIN을 함께 조회할 수 있어야 한다.

8단계에서는 KOSPI 200 기준 스냅샷 전체를 동일 계약의 배포 후보로 검증한다. Fuji에 실제 배포할 대상은 대표 6종목뿐이다.

| 종목 | 코드 | 8단계 처리 |
|---|---:|---|
| 삼성전자 | 005930 | 공식 ISIN 확인 뒤 배포 가능 |
| SK하이닉스 | 000660 | 공식 ISIN 확인 뒤 배포 가능 |
| SK텔레콤 | 017670 | 공식 ISIN 확인 뒤 배포 가능 |
| 현대차 | 005380 | 공식 ISIN 확인 뒤 배포 가능 |
| NAVER | 035420 | 공식 ISIN 확인 뒤 배포 가능 |
| 미래에셋증권 | 006800 | 공식 ISIN 확인 뒤 배포 가능 |

이 문서에서 ISIN을 추측해 채우지 않는다. 배포 시점에 [기준정보 설계](../04-institution-design/REFERENCE_DATA.md)에 따라 공식값과 적용시점을 확인해야 한다.

## 5. 수량 상태

각 지갑의 토큰 수량은 다음 다섯 상태 중 정확히 하나에 속한다.

| 상태 | 의미 | 사용할 수 있는 업무 |
|---|---|---|
| 거래 가능 | 국내 결제와 수탁수량 반영이 모두 확인된 권리 | 승인된 24/7 정산 또는 환매 잠금 |
| 국내 결제 대기 | 체결 후 선발행됐지만 국내 결제, 수탁 확인이 끝나지 않은 권리 | 보유 표시만 가능 |
| 환매 잠금 | 국내 매도와 T+2를 기다리는 권리 | 환매 진행 또는 허용된 취소만 가능 |
| 환매대금 결제 후 소각 대기 | 주식 권리는 종료되고 USD 지급청구로 바뀌었으나 토큰 소각이 남은 상태 | 승인된 소각만 가능 |
| 관리상 동결 | 권리 분쟁, 대사 또는 복구 사유로 사용을 막은 주식 권리 | 승인된 해제, 복구, 기업행동만 가능 |

지갑 전체 동결 표시는 다섯 상태 밖의 여섯 번째 수량이 아니라 사용 제한 표식이다. 동결 전 수량 상태는 그대로 보존한다.

모든 제한 동작은 호출한 통제 계약의 권한과 `MarketPolicyRegistry`의 해당 종목 및 업무범위를 함께 확인한다. 전역 긴급중지 중에는 두 독립 승인을 갖춘 복구 통제만 예외로 허용한다.

## 6. 닫힌 생애주기

### 6.1 발행과 T+2 전환

1. `IntentVerifier`가 고객의 1차 지정가 주문 의사를 검증한다.
2. 국내 주문집행 담당이 체결과 고객별 정수 배분을 확인한다.
3. 위험 담당이 업무 ID와 증거 해시로 T+2 위험을 승인한다.
4. 권리기입 승인 담당이 같은 업무의 고객별 권리기입을 승인한다.
5. 권리 원장 확인 담당이 고객별 수탁권리 원장 반영 완료를 확인한다.
6. `IssuanceController`가 같은 투자자, 종목, 수량과 네 증거를 확인해 `국내 결제 대기`로 발행한다.
7. 국내 결제 담당과 수탁 확인 담당이 서로 다른 증거로 완료를 확인한다.
8. 두 확인이 모두 있을 때 같은 토큰을 재발행하지 않고 `거래 가능`으로 바꾼다.

체결과 배분 확인수량은 발행 상한이다. 네 기관 사실은 같은 업무 ID, 투자자, 종목과 수량을 가리켜야 하며 각 증거는 다른 발행 업무에 재사용할 수 없다.

### 6.2 24/7 2차거래

1. 투자자 주문, 지정 시장조성자 호가와 해외 증권사 정산 승인을 검증한다.
2. 양쪽이 적격이고 한쪽만 지정 시장조성자인지 확인한다.
3. 종목, 방향, 수량, 가격, 금액, 자금경로, 정책버전과 만료가 일치하는지 확인한다.
4. USD 경로는 토큰만 제한 이전한다. USDC 경로는 시험 USDC와 토큰을 같은 거래에서 교환한다.
5. 성공한 체결수량만 세 서명의 nonce와 증거를 소비한다. 부분체결 잔량은 취소한다.
6. 체인 성공 뒤 해외 증권사 권리, 자금 원장 확인이 실패하면 업무상 완료로 표시하지 않고 격리한다.

### 6.3 환매와 소각

1. 고객 환매 의사를 검증하고 거래 가능 수량을 `환매 잠금`으로 옮긴다.
2. 국내 매도대금 T+2 결제와 고객 주식 권리종료를 확인한다.
3. 권리는 USD 지급청구로 전환하고 토큰은 `소각 대기`로 옮긴다.
4. USD 지급 승인과 소각 승인이 연결되면 같은 수량을 소각한다.
5. USD 지급과 소각 중 한쪽만 끝나면 요청을 격리하고 체인 기록을 지우지 않는다.

## 7. 실패 경계

| 실패 지점 | 체인 결과 | 업무상 처리 |
|---|---|---|
| 권리기입 완료 뒤 발행 실패 | 토큰 없음 | 권리만 있는 요청 격리, 같은 업무의 승인된 재실행만 허용 |
| USD 장부 확정 실패 뒤 토큰 이전 성공 | 토큰 이전됨 | 체결 완료 금지, 관련 지갑, 수량 격리와 사람 보정 |
| USDC DvP 실행 실패 | 토큰과 USDC 모두 이전되지 않음 | nonce는 소비되지 않으며 재시도 가능 여부를 원인별 판단 |
| USDC DvP 성공 뒤 권리 원장 실패 | 체인 교환 완료 | 업무상 완료 금지, 관련 수량 격리 |
| 권리종료 뒤 소각 실패 | 소각 대기 토큰 남음 | USD 지급청구와 연결해 격리, 승인된 재실행 |
| RPC 응답 유실 | 결과 불명 | 거래 해시와 이벤트를 조회해 확정 전까지 재전송 금지 |

## 8. 다중체인 경계

LayerZero V2 OFT Burn&Mint는 후속 원칙으로만 남긴다. 단일체인 Fuji PoC에는 브리지 계약을 배포하지 않는다. 후속 다중체인 설계에서도 원천 체인 소각, 목적 체인 적격성, 해외 증권사 권리 원장 승인과 체인 합산 공급량 대사를 모두 확인해야 한다.

## 9. 9단계에 넘기는 입력

- 다섯 수량 상태의 모든 정상, 금지 전환
- 외부 원장과 체인 사이의 부분 완료 및 격리
- 대표 6종목의 주소, 메타정보, 공급량 분리
- 계약별 권한과 독립 승인
- nonce, 업무 ID와 증거 해시 재사용 차단
- 사건별 중지범위와 60초 지연 재개

이 문서와 나머지 8단계 산출물은 2026년 8월 31일 팀 내부 기준으로 함께 승인했다. 9단계에서는 여기서 정한 반례와 불변식을 테스트 명세로 옮긴다.
