# 7단계 공통 데이터 계약

상태: **7단계 팀 내부 승인 완료**

이 문서는 승인된 [업무 상태와 전환 규칙](../05-screens-states-recovery/STATE_MODEL.md)과 [시스템 구조](../06-architecture-security/ARCHITECTURE.md)를 시스템이 함께 쓰는 데이터로 옮긴다. 데이터 형식은 [JSON Schema](specs/schemas/)가 기계 판독 기준이며 이 문서는 각 값의 업무 의미를 설명한다.

[기계 추적표](specs/traceability.json)는 각 상태축을 조회, 명령과 이벤트에 연결하고 6단계 구성요소가 실제 계약을 하나 이상 갖는지 확인한다.

## 1. 기준과 우선순위

- 1~6단계 승인 문서는 고객 권리, 기관 책임과 상태의 의미를 정한다.
- 이 문서는 같은 의미를 공통 이름과 자료형으로 정한다.
- JSON Schema는 필드, 필수 여부와 허용값의 기준이다.
- OpenAPI와 AsyncAPI는 각각 HTTP와 비동기 메시지 전달의 기준이다.
- 명세끼리 충돌하면 구현자가 임의로 선택하지 않고 7단계 승인을 보류한다.
- 고객별 수탁권리 원장은 계속 인가 해외 증권사의 기준 기록이다. 토큰과 플랫폼 데이터는 이를 대체하지 않는다.

## 2. 이름, 식별자와 시간

| 구분 | 규칙 | 예시 |
|---|---|---|
| JSON 필드 | 영문 `lowerCamelCase` | `workflowId`, `shareQuantity` |
| 기계 상태 | 영문 `UPPER_SNAKE_CASE` | `SETTLEMENT_PENDING` |
| 화면 상태 | 기계 상태마다 한국어 이름을 하나 연결 | `SETTLEMENT_PENDING` → `국내 결제 대기` |
| 식별자 | RFC 4122 UUID 문자열 | 요청, 주문, 이벤트, 증거와 업무 식별자 |
| 종목 식별자 | KRX 6자리 종목코드와 공식 ISIN | ISIN 미확인 상품은 활성화 금지 |
| 체인 주소 | `0x`로 시작하는 20바이트 EVM 주소 | Fuji 지갑과 계약 |
| 증거 해시 | `0x`와 64자리 16진수 SHA-256 | 원문을 공개하지 않는 연결값 |
| 시각 | UTC RFC 3339와 `Z` | `2026-08-31T03:00:00Z` |
| 국내 업무일 | `YYYY-MM-DD`, 해석 시간대는 `Asia/Seoul` | KRX 거래일, 월말, 제출기한 |

내부 시각은 UTC로 저장한다. KRX 거래일, 다음 달 10일 보고기한과 국내 영업일 판단만 `Asia/Seoul`을 명시해 계산한다.

## 3. 수량과 금액

- `shareQuantity`는 0 이상의 정수 문자열이다. 주문과 이전 수량은 1 이상이어야 한다.
- `1주 = 고객 수탁권리 1단위 = 권리토큰 1단위`를 유지한다.
- JavaScript 부동소수점으로 금액이나 수량을 계산하지 않는다.
- 금액은 `currency`, `amountMinor`, `decimals`를 함께 가진다.

| 통화 | `decimals` | `amountMinor` 예시 | 표시값 |
|---|---:|---:|---:|
| KRW | 0 | `257000` | 257,000원 |
| USD | 2 | `18619` | 186.19달러 |
| USDC | 6 | `186190000` | 186.190000 USDC |

환율은 금액과 분리된 십진 문자열로 보관한다. 기준통화, 상대통화, 값, 기준시각과 유효기한을 함께 기록한다.

## 4. 공통 업무 식별자

| 이름 | 의미 | 생성 주체 |
|---|---|---|
| `requestId` | HTTP 요청 한 건 | API 경계 |
| `workflowId` | 처음부터 최종 완료까지 이어지는 업무 | 업무 조정기 |
| `correlationId` | 기관 요청, 이벤트와 체인 거래를 같은 업무로 묶는 값 | 최초 명령 수신자 |
| `causationId` | 현재 이벤트를 만든 바로 이전 명령 또는 이벤트 | 이벤트 생산자 |
| `eventId` | 비동기 이벤트 한 건 | 이벤트 생산자 |
| `sourceRecordId` | 원본기관이 부여한 기록번호 | 원본기관 또는 모의 어댑터 |
| `evidenceId` | 기관 확인이나 사람 승인 증거 | 증거 저장소 |
| `aggregateVersion` | 같은 업무대상의 변경 순서 | 해당 업무 모듈 |
| `sourceSequence` | 같은 기관 이벤트 흐름의 증가 순번 | 모의 기관 어댑터 |

식별자는 서로 대신 쓸 수 없다. 예를 들어 체결번호를 토큰 발행 승인번호로 재사용하지 않는다.

## 5. 기관 사실과 증거

모든 체결, 자금, 결제, 수탁, 기업행동과 사람 승인은 다음 출처정보를 가진다.

| 필드 | 의미 |
|---|---|
| `sourceInstitutionId` | 사실을 책임지는 기관 또는 모의기관 |
| `sourceRecordId` | 기관 원기록 번호 |
| `asOf` | 사실이 적용되는 기준시각 |
| `receivedAt` | 플랫폼이 받은 시각 |
| `validUntil` | 신규 업무에 사용할 수 있는 마지막 시각. 만료가 없으면 생략 |
| `policyVersion` | 판정이나 통제에 적용한 정책 |
| `correctsEventId` | 정정하는 이전 이벤트. 최초 결과면 생략 |
| `evidenceHash` | 원문 증거의 비식별 해시 |
| `simulation` | PoC에서는 항상 `true` |

정정은 원기록을 덮어쓰지 않는다. 정정 이벤트와 기존 이벤트를 모두 보존하고 영향을 받는 주문, 권리, 토큰, 자금과 보고를 다시 계산한다.

## 6. 독립 상태축

하나의 거대한 상태값을 만들지 않는다. 다음 상태축은 각각 현재상태와 변경이력을 가진다.

1. 고객 적격성과 투자자 보호
2. 계좌와 전용 지갑 연결
3. 상품 공통, 1차 발행, 24/7 거래와 환매 가능 여부
4. 고객 원주문, 취합주문과 국내 체결
5. 국내 체결과 고객별 배분 확인
6. T+2 위험 승인, 권리기입 승인과 실제 원장 기입 완료 확인
7. 토큰 발행, 잠금, 거래 가능, 이전과 소각
8. 국내 결제와 수탁수량 확인
9. USD 및 USDC 자금 예약과 확정
10. 시장조성자 호가, 재고, 순포지션과 헤지
11. 환매, 지급청구, 소각과 USD 지급
12. 배당, 의결권, 기업행동과 월별 보고
13. 두 축 대사, 중지, 격리, 보정과 재개

각 기계 상태는 [상태 모델](../05-screens-states-recovery/STATE_MODEL.md)의 한국어 상태와 연결한다. [상태 카탈로그](specs/state-catalog.json)가 실제 목록의 기계 기준이고, `specs/schemas/domain.schema.json`의 `StateCatalogEntry`가 각 항목의 형식을 검사한다. 같은 한국어 상태명이 여러 업무축에서 쓰이면 축마다 다른 기계 상태로 구분한다.

## 7. 주요 업무 자료

| 자료 | 최소 내용 | 기준 기록 |
|---|---|---|
| 고객과 지갑 | 합성 고객 ID, 권리계정 참조, 활성 지갑, 적격성 만료 | 해외 증권사 계좌와 적격성 기록 |
| 위험공시와 동의 | 공시 ID, 버전, 적용기간, 책임기관, 고객 동의시각과 만료 | 해외 증권사의 공시 원본과 고객별 전자 동의 |
| 민원 | 민원 ID, 종류, 상태, 책임기관, 관련 주문과 공시 버전, 답변 및 정정 참조 | 투자자 민원 원기록과 책임기관 처리 기록 |
| 상품 | 종목코드, ISIN, 기준정보 버전, 기능별 가능상태, 토큰주소 | 공식 기준정보와 해외 증권사 상품판정 |
| 1차 주문 | 정수수량, KRW 지정가격, 대상 거래일, 자금경로, 원주문과 취합 연결 | 해외 증권사 주문기록과 국내 체결 |
| 발행 확인 | 국내 체결과 고객별 정수 배분, T+2 위험 승인, 권리기입 승인, 실제 원장 반영 완료와 발행 증거 | 국내 주문집행 증권사, 해외 증권사 고객별 수탁권리 원장과 토큰 실행기록 |
| T+2 확인 | 국내 결제와 수탁수량의 서로 다른 기관 사실 | KSD 및 수탁기관 확인 |
| 24/7 주문 | 지정 시장조성자 호가, 투자자 서명, 결제완료 수량과 자금예약 | 해외 증권사 권리 및 자금 장부와 체인 결과 |
| 환매 | 잠금수량, 국내 매도, 결제, 지급청구, 소각과 USD 지급 | 권리 원장, 국내 수량과 고객 USD 장부 |
| 권리업무 | 기준일 스냅샷, 배당총액, 의결권 지시, 기업행동과 보고증거 | 국내 배정과 해외 증권사 기록 |
| 대사 | 두 축의 입력, 차이, 중지범위와 재개 승인 | 각 기준 기록의 같은 기준시각 사본 |

API의 UUID는 canonical `8-4-4-4-12` 문자열로 주고받는다. 블록체인 연계 모듈은 하이픈을 제거한 32자리 16진수 값을 `bytes16`으로 변환하고 역변환 때 같은 canonical 소문자 UUID를 복원한다. 유효한 UUID가 아니거나 왕복 결과가 다르면 체인 요청을 만들지 않는다. 증거 해시는 `bytes32`, 지갑과 계약은 `address`, 수량과 최소단위 금액 및 nonce는 `uint256`, 만료시각은 Unix seconds `uint256`으로 변환한다.

## 8. 투영과 완전성

조회용 자료는 기준 기록의 사본 또는 플랫폼 계산 결과다. 모든 조회 응답에는 다음 값을 넣는다.

- `projectionAsOf`: 조회자료의 기준시각
- `lastEventSequence`: 마지막으로 반영한 내부 이벤트 순번
- `projectionStatus`: `CURRENT`, `INCOMPLETE`, `STALE`
- `missingSequences`: 순번 공백이 있을 때 누락구간

`INCOMPLETE` 또는 `STALE` 자료는 조회와 감사에는 사용할 수 있지만 신규 발행, 24/7 정산, 환매 소각과 지급의 근거로 사용할 수 없다.

## 9. 금지 데이터

공유 API, 이벤트, 로그와 온체인 입력에는 다음을 넣지 않는다.

- 실제 이름, 생년월일, 주소, 연락처와 여권번호
- 실제 국적, 조세거주지와 제재조회 원문
- 실제 은행계좌와 증권계좌 번호
- 여권번호 또는 고유식별정보의 해시
- 개인키, 니모닉, 전체 인증토큰과 기관 원문

JSON Schema는 정의하지 않은 필드를 거절하고 예시와 자동검증은 금지된 필드명이 나타나는지도 검사한다.

## 10. EIP-712 서명 계약

공통 도메인은 다음 값을 사용한다.

- `name`: `Korean Equity RWA PoC`
- `version`: `1`
- `chainId`: `43113`
- `verifyingContract`: 다섯 서명형에 공통으로 사용하는 배포된 Fuji `IntentVerifier` 주소

서명형은 `PrimaryOrderIntent`, `SecondaryOrderIntent`, `RedemptionIntent`, `MarketMakerQuote`, `BrokerSettlementApproval` 다섯 개다. 정확한 필드와 Solidity 자료형은 [서명 스키마](specs/schemas/signatures.schema.json)가 정한다.
[정상 서명 예시](specs/examples/signed-intents.json)는 다섯 형식과 `primaryType` 및 본문의 일치를 함께 검증한다.

- 주문과 승인은 종목 또는 토큰, 정수수량, 가격 또는 지급금액, 자금경로, nonce, 만료와 정책버전에 묶는다.
- 투자자 방향은 `INVESTOR_BUYS` 또는 `INVESTOR_SELLS`로 표현한다.
- 시장조성자 호가 방향은 `MM_BUYS` 또는 `MM_SELLS`로 표현해 투자자 방향과 혼동하지 않는다.
- USD는 영주소를 지급자산으로 쓰지 않고 `paymentMode=USD_LEDGER`, USDC는 `paymentMode=USDC_ONCHAIN`과 실제 시험토큰 주소를 사용한다.
- 같은 signer와 서명형에서 nonce를 한 번만 사용할 수 있다.
- `IntentVerifier`는 서명 도메인, 만료와 nonce를 공통으로 검증하며 실제 발행, 2차 정산과 환매 실행은 기능별 통제 계약이 담당한다.
- 컨트랙트 함수와 역할 상수는 8단계에서 정한다.

## 11. 버전 규칙

- HTTP 기본경로는 `/api/v1`이다.
- JSON Schema 묶음은 `1.0.0`, 이벤트 이름은 `.v1`로 시작한다.
- 선택 필드 추가는 하위호환 변경이다.
- 필드 삭제, 의미 변경, 필수 필드 추가와 enum 축소는 새 주요버전이 필요하다.
- 알 수 없는 선택 필드는 보관하지 않아도 되지만 알 수 없는 주요버전 이벤트는 격리한다.

## 12. 승인 기준

- [x] 상태축과 한국어 상태가 기계 상태에 빠짐없이 연결된다.
- [x] 수량과 금액에 부동소수점을 사용하지 않는다.
- [x] 모든 기관 사실에 출처, 시각, 정정과 증거 정보가 있다.
- [x] EIP-712 서명에 체인, 계약, nonce, 만료와 정책버전이 포함된다.
- [x] 고객 권리 원장과 플랫폼 투영의 우선순위가 뒤바뀌지 않는다.
- [x] 공유 schema에 개인정보와 원문 계좌정보가 없다.

이 문서와 API 및 이벤트 계약을 함께 승인했으므로 8단계 스마트컨트랙트 설계를 시작할 수 있다.
